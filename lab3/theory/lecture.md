# Контрольные вопросы по лекции

Короткие ответы по слайдам «Контейнеризация» (лекции 6–7).

## a. Компоненты платформы Docker

Docker упаковывает приложение вместе с зависимостями в контейнер и даёт команды, чтобы этим контейнером управлять. На слайдах это не одна программа, а цепочка.

**Клиент** (`docker`) — командная строка. Он принимает `docker run`, `docker build`, `docker ps`, собирает запрос и отправляет его демону. Сам контейнер клиент не создаёт. По умолчанию запрос идёт в сокет `/var/run/docker.sock`, можно настроить и доступ по TCP.

**Демон** (`dockerd`) принимает запросы и ведёт образы, контейнеры, сети и тома, а также вход в реестры. Сам с ядром он контейнер не собирает: эту работу отдаёт ниже.

**containerd** — рантайм, вынесенный из Docker. Он скачивает образы, хранит слои, создаёт, запускает, останавливает и удаляет контейнеры. Тот же containerd использует Kubernetes.

Объекты, которыми управляет эта связка:

- **образ** — неизменяемый шаблон;
- **контейнер** — запущенный экземпляр образа;
- **сеть**;
- **том**;
- **реестр** — сервер, откуда образы скачивают и куда их отправляют. По умолчанию это Docker Hub (`docker pull`, `docker tag`, `docker push`).

Раньше Docker сидел на LXC. С 2015 года своя библиотека libcontainer, затем переход к модульной схеме вокруг стандартов OCI.

## b. Образы Docker

Образ — неизменяемый шаблон: минимальная ОС, библиотеки, код и настройки. Хранится в реестре, локально появляется после `docker pull` или `docker build`.

Образ собран из слоёв. Каждый слой — изменение файловой системы. Слои склеивает union-файловая система: в Linux это OverlayFS, раньше в Docker был AUFS, для блочных устройств — Device Mapper.

**Copy-on-write:** контейнеры одного образа читают общие слои. Файл переписывается только у того контейнера, который его меняет, и копия лежит уже в его слое. На слайде пример: образ 500 МБ и два контейнера с 10 и 20 МБ правок занимают 530 МБ, а не два полных образа.

Имя образа — репозиторий и тег, например `nginx:latest`. `docker tag` даёт тому же образу другое имя, `docker push` отправляет его в реестр.

## c. Жизненный цикл контейнера

Контейнер — запущенный экземпляр образа. Он изолирован, использует общее ядро и живёт, пока жив процесс, вокруг которого его создали.

Внутри этот процесс имеет PID 1. Рядом можно запустить другие процессы, но если остановить или перезапустить именно PID 1, контейнер завершается. Каталоги внутри выглядят как у обычного дистрибутива, с которого взят образ.

Команды со слайда:

- `docker run` — создать и запустить;
- `docker ps -a` — список, в том числе остановленных;
- `docker stop` / `docker start` / `docker restart`;
- `docker rm` — удалить;
- `docker logs` — журнал;
- `docker exec` — команда внутри уже работающего контейнера.

Данные, которые процесс создал внутри, остаются в контейнере и сами по себе больше нигде не пишутся. После удаления контейнера их нет, если путь не вынесен в том.

## d. Режимы запуска

На слайдах долгоживущий сервис запускают в фоне: `docker run -d`. Клиент при этом не держит терминал, контейнер остаётся у демона. Оболочку внутри уже запущенного контейнера открывают так: `docker exec -it ... bash`.

Контейнер рассчитан на один главный процесс. Если завершился PID 1, контейнер выходит, даже если рядом успели появиться другие процессы.

Изоляцию дают пространства имён: свои PID, сеть, файловая система, hostname, пользователи и IPC. Потолок по ресурсам задают cgroups. Пример со слайда: `docker run --cpus=2 --memory=1g --memory-swap=2g nginx`.

## e. Типы сетей Docker

Сеть Docker — виртуальная сеть: контейнеры изолированы друг от друга и при этом могут общаться. Драйверы со слайда:

- **bridge** — сеть по умолчанию на одном хосте;
- **host** — контейнер сидит в сети хоста, без своей изоляции адресов;
- **overlay** — одна сеть на несколько хостов (Swarm, Kubernetes);
- **none** — сети нет;
- **macvlan** — у контейнера свой MAC-адрес в физической сети.

Проброс портов публикует порт контейнера на хосте: `-p 8080:80` означает порт 8080 хоста и порт 80 контейнера. `-P` публикует порты, указанные в `EXPOSE`. Можно привязать публикацию к конкретному адресу, например `127.0.0.1:8080:80`.

## f. Docker Compose

Compose описывает приложение из нескольких контейнеров в YAML и одной командой поднимает или останавливает всё сразу.

В файле со слайда у сервиса есть образ, команда, порты, рабочий каталог, том и переменные окружения. Имя соседнего сервиса (`MYSQL_HOST: mysql`) — это имя, по которому контейнеры находят друг друга.

Так собирают связанный набор: приложение, база, веб-сервер. Описание лежит в файле, а не в длинной цепочке отдельных `docker run`.

## g. Infrastructure as Code и Docker

В лекции это звучит как неизменяемая инфраструктура и CI/CD.

Проблема, которую закрывает Docker: «у меня работает» и конфликт версий библиотек. Приложение упаковано со всеми зависимостями, контейнер одинаково запускается в разработке, тесте и продакшене. Зависимости фиксирует Dockerfile.

Образ не правят на месте. Нужна новая версия — собирают новый образ. Отсюда предсказуемость: что собрали, то и запускается.

В CI/CD контейнер проходит тот же путь: сборка образа, тесты в изолированной среде, публикация в реестр, запуск в production. Инструменты со слайда — Jenkins, GitLab CI, GitHub Actions. Артефакт пайплайна — образ.

Compose-файл делает то же для нескольких сервисов: стенд описан текстом и поднимается одной командой.

## h. Dockerfile и сборка образа

Dockerfile — инструкции, по которым собирается образ. `docker build -t имя .` выполняет их по порядку. `RUN` создаёт слой, поэтому установка пакетов остаётся в образе.

Инструкции со слайда:

- `FROM` — базовый образ, с него начинается рецепт;
- `LABEL` — подпись (кто собрал и поддерживает);
- `ENV` — переменная среды;
- `ARG` — переменная на время сборки;
- `RUN` — команда при сборке, результат становится слоем;
- `COPY` — файлы и каталоги в образ;
- `ADD` — то же плюс URL и распаковка локального tar;
- `WORKDIR` — текущий каталог для следующих шагов;
- `EXPOSE` — какой порт образ считает своим;
- `VOLUME` — точка, которую при запуске выносят в постоянное хранилище;
- `CMD` — команда по умолчанию при старте контейнера, её можно заменить в `docker run`, в файле она одна;
- `ENTRYPOINT` — команда, которая выполняется всегда, аргументы из `docker run` к ней добавляются.

На слайде рекомендуют `COPY`, а `ADD` брать, только когда нужны URL или распаковка архива.

## i. Эфемерность контейнеров и хранение данных

Контейнер по умолчанию состояние не хранит. Файл, созданный процессом внутри, живёт в контейнере. Удалили контейнер — этих данных нет. На слайдах это названо ограничением контейнеризации: для постоянных данных нужен внешний том.

Куда выносят данные:

- **именованный том** — его создаёт и ведёт Docker (`docker volume create`). Данные остаются после удаления контейнера, один том можно подключить нескольким контейнерам. Вариант для постоянных данных;
- **анонимный том** — Docker создаёт его сам, для временных данных;
- **bind mount** — каталог хоста напрямую виден в контейнере (`-v $(pwd):/app`). Удобно в разработке: правка на хосте сразу видна внутри. Зависит от путей и прав этой машины;
- **tmpfs** — данные в памяти, на диск не пишутся и после остановки пропадают.

Именованный том переносимее и им управляет Docker. Bind mount проще для разработки и привязан к конкретному хосту.
