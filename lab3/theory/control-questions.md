# Контрольные вопросы к лабораторной работе №3

Разбор вопросов по платформе Docker: клиент и демон, образы, жизненный цикл контейнера, сети, Compose и хранение данных.

## a. Компоненты платформы Docker

Docker — не одна программа. Команда `docker` только передаёт просьбу. Контейнер создаёт другая служба, образ хранит третья, а процесс внутри контейнера запускает ещё одна, короткая.

**Клиент** — команда `docker` и команда `docker compose`. Они читают аргументы и файлы в каталоге (`Dockerfile`, `compose.yaml`) и отправляют запрос демону. Сами они не держат сервер и не распаковывают слои. После `docker run -d` клиент заканчивается, а контейнер остаётся. Связь с демоном идёт через сокет `/var/run/docker.sock`. Группа `docker` даёт право писать в этот сокет без `sudo`. Пока группа не применилась в сессии, новый вход нужен именно из-за сокета, а не из-за самой команды.

**Демон** — `dockerd`, служба `docker`. Он принимает запросы клиента, качает образы, собирает слои, заводит сети и тома, помнит контейнеры после закрытия терминала. `docker ps -a` показывает список, который ведёт демон, а не оболочка.

**Реестр** — хранилище образов вне машины. Имя без адреса сервера клиент относит к Docker Hub: так устроены имена вроде `nginx`, `mariadb`, `nextcloud`. Имя с адресом хоста идёт в другой реестр, например `ghcr.io/...`. Свой образ уходит в реестр командами `docker tag` и `docker push`. Реестр хранит слои и подпись «этот тег указывает на вот этот набор слоёв». Запущенных контейнеров в реестре нет.

Поверх демона лежат четыре объекта платформы.

**Образ** — неизменяемый шаблон файловой системы и команда запуска. Образ собирают локально или получают из реестра. Удалить его можно, когда на него не опирается контейнер.

**Контейнер** — запущенный или уже завершившийся экземпляр образа. У него есть имя, своя сеть, свой изменяемый слой поверх образа и один главный процесс. Два контейнера одного образа делят слои образа и не делят изменяемый слой.

**Том** — место для данных, которое переживает удаление контейнера. Каталог хоста можно примонтировать внутрь (bind mount). Именованный том заводит сам Docker, и путь на хосте выбирает демон. Файл, записанный в контейнер мимо тома, живёт в изменяемом слое и пропадает вместе с контейнером.

**Сеть** — отдельный коммутатор демона. Одиночный `docker run` по умолчанию попадает в сеть `bridge`. Проект Compose получает свою сеть, и в ней имена сервисов превращаются в адреса. С хоста эти имена не открываются: снаружи ходят на `localhost` и на опубликованный порт.

**Docker Engine** — имя всей связки: клиент, демон, API демона, сборка образов, сети и тома. В дистрибутивах тот же движок часто упакован как `moby-engine`: команда в терминале всё равно `docker`, служба всё равно `dockerd`. Пакет Compose даёт подкоманду `docker compose`. Это тот же Engine, только собранный дистрибутивом, а не взятый из репозитория Docker CE.

Демон не запускает процесс контейнера собственными руками. Он просит **containerd**.

containerd — отдельный демон. Он хранит слои как содержимое по адресу-хешу, собирает из них снимок файловой системы и следит за жизненным циклом контейнера. Сборку `Dockerfile`, публикацию портов и compose-файл containerd не разбирает: это остаётся работой dockerd. Разделение нужно ещё и потому, что Kubernetes пользуется containerd напрямую, без dockerd.

**runc** — программа, которая один раз создаёт контейнер по стандарту OCI. Она получает каталог со корневой файловой системой и файлом `config.json`: какая команда, какие пространства имён, какие лимиты. runc создаёт процесс, настраивает ему изоляцию и завершается. Дальше веб-сервер или база — обычные процессы хоста. Их родитель после выхода runc — маленький процесс-прокладка containerd-shim. Прокладка нужна, чтобы перезапуск dockerd не убил уже запущенные контейнеры.

Цепочка одного `docker run` такая. Клиент пишет в сокет. dockerd находит образ или качает его из реестра, просит containerd подготовить корневую файловую систему и сеть. containerd вызывает runc. runc запускает главный процесс. Клиент к этому моменту уже напечатал идентификатор контейнера и, если указан `-d`, отпускает терминал.

## b. Образы Docker

Образ собирается стопкой. Короткий рецепт веб-сервера выглядит так:

```dockerfile
FROM nginx:alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY index.html /usr/share/nginx/html/index.html
EXPOSE 8080
```

`docker history` показывает эту стопку. Каждая строка, которая меняет файлы, становится **слоем**. `FROM` приносит уже готовую стопку слоёв базового образа. Каждый `COPY` добавляет свой слой. `EXPOSE` слой файлов не создаёт: это подпись в метаданных.

Слои только для чтения и адресуются содержимым. Если два образа стоят на одном и том же базовом слое, на диске этот слой лежит один раз. Контейнеры, запущенные из этих образов, читают одни и те же нижние слои.

Склеивает стопку **union-файловая система**. На современном Docker это overlayfs. У каталога, который видит процесс в контейнере, есть нижние каталоги (слои образа) и верхний каталог (изменяемый слой этого контейнера). Чтение файла идёт сверху вниз: если файл есть в верхнем слое, берётся он, иначе поиск продолжается в нижних. Запись в файл из нижнего слоя сначала копирует файл наверх, и дальше меняется уже копия. Это и есть **copy-on-write**. Удаление файла из нижнего слоя не стирает слой: наверху появляется белая метка, и склеенный каталог делает вид, что файла нет. Поэтому образ после `docker build` не переписывается, сколько бы контейнеров от него ни запустили. `docker rm` удаляет верхний каталог контейнера. Слои образа остаются, и следующий `docker run` получает чистый верх.

**Базовый образ** — тот, кто указан во `FROM`, и вся его родословная. `alpine` — маленький дистрибутив. `nginx:alpine` — тот же Alpine плюс Nginx и его конфиги. Своя страница не собирает сервер из исходников: она принимает уже собранный образ и кладёт сверху файлы. Официальные образы баз и приложений устроены так же, только их рецепт написал сопровождающий образа.

**Тег** — имя, которое указывает на конкретный образ. Запись `репозиторий:тег`, например `nginx:alpine` или `alpine:3.20`. Если тег не написан, демон подставляет `latest`. `docker tag` не копирует слои, а добавляет второе имя тому же образцу. Завтра `latest` может указывать уже на другую сборку. Тег — метка, а не отпечаток содержимого.

**Идентификатор** — хеш содержимого. У локального образа есть `Id`, длинный `sha256:...`. У манифеста в реестре есть свой digest. Манифест перечисляет слои и конфиг. Пока байты слоёв те же, digest тот же. `docker pull имя@sha256:...` берёт ровно эту сборку, даже если владелец тега уже отправил новую. Тегом пользуются в обычной работе. Digest нужен, когда одну и ту же сборку надо повторить спустя время.

**Реестр** отдаёт и принимает манифесты и слои по HTTPS. Docker Hub — реестр по умолчанию и одновременно сайт со страницей образа. Имя `пользователь/репозиторий` значит: реестр Hub, владелец и имя репозитория. Имя с хостом в начале, как `ghcr.io/...`, значит другой реестр. Локальный образ в реестре не появляется, пока его не пометили именем вида `<логин>/<репозиторий>` и не выполнили `docker push`. Push отправляет только те слои, которых у реестра ещё нет.

Получение симметрично. `docker pull` качает манифест и недостающие слои. `docker run` с образом, которого нет локально, делает pull сам. Образ, произведённый `docker build` на этой машине, pull не требует.

## c. Жизненный цикл контейнеров

Контейнер для демона — запись с состоянием. Процесс внутри может уже закончиться, а запись ещё лежать в `docker ps -a`.

Состояния:

- **created** — запись есть, главный процесс не запущен. На этом останавливается `docker create`.
- **running** — главный процесс жив. Так работает сервер, пока его не остановят.
- **paused** — процесс заморожен целиком, через cgroup freezer. Память и открытые файлы остаются. Это не остановка: порт ещё занят, процесс не получил сигнал завершиться. Снимает заморозку `docker unpause`.
- **exited** — главный процесс завершился. Команда вроде `echo`, которая печатает строку и выходит, сразу оказывается здесь. В `docker ps` такого контейнера нет, в `docker ps -a` он есть, вместе с кодом выхода.
- **restarting** — процесс умер, а политика перезапуска велит поднять его снова. Контейнер на короткое время виден в этом состоянии, затем снова `running` или, после исчерпания попыток, `exited`.

Переходы прямые. `create` даёт `created`. `start` переводит `created` или `exited` в `running`. `docker run` сливает создание и старт. `stop` переводит `running` в `exited`. Повторный `start` поднимает тот же контейнер с тем же изменяемым слоем. `rm` удаляет запись и изменяемый слой. Удалить обычной командой можно вышедший контейнер. `docker rm -f` сначала останавливает, потом удаляет.

**Главный процесс** — PID 1 внутри контейнера. Контейнер жив, пока жив он. Exec-форма `CMD ["echo", "..."]` запускает программу напрямую, без оболочки, и эта программа становится PID 1. У серверных образов входной сценарий в конце подменяет себя сервером, и сервер становится PID 1. Когда PID 1 завершается, containerd помечает контейнер как `exited`. Остальные процессы контейнера получают завершение вместе с ним.

`docker exec` запускает добавочный процесс рядом с PID 1. Клиент базы, запущенный так, подключается к уже работающему серверу, выполняет запрос и сам заканчивается. Сервер остаётся PID 1. Если бы завершился сервер, контейнер перешёл бы в `exited`, даже если клиент ещё что-то печатал.

PID 1 в Linux получает ещё одну обязанность: он должен забирать завершившихся потомков и принимать сигналы. Обычный процесс, который не является PID 1, получает действие по умолчанию на многие сигналы и не видит чужих зомби. Поэтому образ устроен так, чтобы сервер был PID 1, а не чтобы перед ним всю жизнь висела оболочка `sh -c`. Оболочка без передачи сигнала съедает `SIGTERM` сама и не отдаёт его серверу. Exec-форма `CMD` обходит оболочку.

**Корректная остановка** — `docker stop`. Демон посылает PID 1 сигнал `SIGTERM` и ждёт, по умолчанию 10 секунд. Веб-сервер закрывает соединения и выходит. База сбрасывает грязные страницы и останавливает движок, после чего файлы данных согласованы. Если процесс за это время не вышел, демон посылает `SIGKILL`. `SIGKILL` процесс не перехватывает: ядро снимает его сразу.

**Принудительная остановка** — `docker kill`. По умолчанию это сразу `SIGKILL`, без ожидания и без `SIGTERM`. Для базы это то же самое, что снять питание. Журнал InnoDB при следующем старте доиграет сам, но транзакция, которая не успела зафиксироваться, откатится. Для процесса, который и так уже завершился, разницы между `stop` и `kill` нет. Для сервера базы она есть.

`docker restart` — это stop и затем start того же контейнера. Изменяемый слой и примонтированные каталоги сохраняются. Новый контейнер получился бы только из нового `docker run`.

## d. Режимы запуска контейнеров

**Фоновый режим** включает ключ `-d`. Клиент просит демон запустить контейнер и сразу возвращает терминал. Вывод процесса в этот терминал не течёт, его забирает `docker logs`. Порт слушается и после закрытия окна: процесс держит демон, а не сессия оболочки. Так запускают веб-сервер, базу и остальные долгоживущие сервисы. `docker compose up -d` делает то же для всего проекта.

**Интерактивный режим** — ключи `-it`. `-i` оставляет открытым стандартный ввод, `-t` выделяет терминал, чтобы у программы были управляющие последовательности. Так запускают оболочку (`docker run -it образ sh`) и программы, которые рисуют интерфейс в терминале и читают нажатия. Пока такая программа работает, терминал занят. Её завершение переводит контейнер в `exited`.

Запуск на переднем плане без `-it` тоже возможен. Клиент просто ждёт, пока главный процесс закончится, и показывает его вывод. Короткой команде вроде `echo` ввод не нужен, поэтому терминал ей не выделяют.

**Одноразовый контейнер** существует ради одного действия: напечатать строку, выполнить запрос, прогнать сборку, сыграть сессию. Образ после этого остаётся, запись контейнера можно удалить. Повторять действие — значит создать новый процесс.

**Долгоживущий контейнер** держит сервер. Его PID 1 не должен завершаться после настройки. Официальные образы поэтому запускают сервер на переднем плане внутри контейнера, а не уводят его в фон классического демона Unix. Если родительский сценарий закончился, контейнер сразу становится `exited`, даже когда где-то в фоне ещё висит процесс.

**Политика перезапуска** говорит демону, что делать, когда PID 1 умер или когда перезапустилась сама служба `docker`.

- `no`, значение по умолчанию. Контейнер остаётся `exited`.
- `on-failure` поднимает контейнер снова, только если код выхода ненулевой. Успешный конец с кодом 0 его не перезапустит.
- `always` поднимает контейнер и после падения, и когда снова стартовал демон. Остановленный вручную контейнер с этой политикой после перезапуска демона тоже поднимется.
- `unless-stopped` делает то же, пока контейнер не остановлен вручную. После `docker stop` перезапуск демона оставляет его выключенным.

Политика не создаёт второй контейнер. Она снова переводит ту же запись в `running`. Задают её ключом `--restart` или полем `restart` в Compose.

**Ограничение ресурсов** делает cgroup, не образ. Ключи `--memory`, `--cpus`, `--pids-limit` ставят потолок этому контейнеру. Без потолка контейнеры делят процессор и память хоста, пока ядро само не начнёт отбирать память. Исчерпание лимита памяти завершает процессы контейнера. Исчерпание квоты CPU его не убивает, а замедляет.

**Изоляция** — набор пространств имён Linux, которые runc включает процессу.

- PID: внутри контейнера свой список процессов, PID 1 — его главный процесс. Процессы хоста снаружи он не видит.
- Mount: свой корень файловой системы, собранный из слоёв и томов. Каталог хоста виден только там, куда его примонтировали.
- Network: свой стек, свои порты, свой `localhost`. `localhost` внутри контейнера — это он сам, а не хост.
- UTS: своё имя хоста.
- IPC: своя разделяемая память.

Пользовательское пространство имён Docker по умолчанию не включает. Root внутри контейнера — это uid 0 на хосте, только с урезанными возможностями. Защита держится на capabilities и на том, что монтирования и устройства контролирует демон.

**Привилегии.** Обычный контейнер не может грузить модули ядра, перенастраивать сеть хоста и читать чужие диски. Ключ `--privileged` снимает почти все эти запреты и отдаёт устройства. Отдельная дыра в изоляции — сокет демона. Контейнеру, которому примонтировали `/var/run/docker.sock`, можно просить демон запускать любые контейнеры, в том числе привилегированные. Снаружи у такого контейнера обычный опубликованный порт, а сокет рядом делает его администратором всего Docker на машине.

## e. Типы сетей Docker

Демон умеет несколько **драйверов**.

**bridge** — коммутатор на хосте и пара виртуальных кабелей `veth` до каждого контейнера. Контейнер получает адрес из диапазона моста, у сети по умолчанию это обычно `172.17.0.0/16`. Выход в интернет идёт через трансляцию адресов хоста. Одиночный `docker run` без `--network` попадает сюда. Адрес моста со стороны хоста, часто `172.17.0.1`, контейнер видит как соседний адрес: так процесс в контейнере добирается до службы, которая слушает на хосте.

**Сеть проекта Compose** — тоже bridge, только свой. Сервисы одного файла сидят в ней вместе. Контейнер из другого `docker run` имя сервиса не резолвит, даже если оба запущены на одной машине. Своя сеть и есть граница.

Остальные драйверы:

- **host** отдаёт контейнеру сетевое пространство имён хоста. Порт внутри совпадает с портом машины, публиковать его не нужно. Изоляции адресов нет.
- **none** не выдаёт интерфейсов, кроме петли. Контейнеру некуда отправить пакет.
- **overlay** строит одну сеть поверх нескольких хостов. Его использует Swarm.
- **macvlan** и **ipvlan** выдают контейнеру адрес прямо в физической сети, как отдельной машине на коммутаторе. Мост Docker и трансляция портов при этом не стоят посередине.

**Изоляция сетей** означает, что демон не маршрутизирует пакеты между двумя bridge сам. Опубликованный порт — отдельное правило, и оно ведёт с хоста в конкретный контейнер, а не открывает всю внутреннюю сеть наружу. Сервис без секции `ports` с хоста по `localhost` недоступен. Сосед по той же сети достаёт его по имени сервиса и по внутреннему порту.

**Взаимодействие контейнеров** на одной сети идёт по их адресам. Имена выдаёт встроенный DNS демона, `127.0.0.11` с точки зрения контейнера. Имя сервиса из compose-файла становится именем. Прокси поэтому пишет `proxy_pass http://имя-сервиса:порт`. Это имя существует, пока оба контейнера в одной сети. С хоста оно не откроется.

**Публикация портов** — правило на хосте: пакет на порт хоста переписывается в адрес контейнера и в его порт. В записи `-p 8080:80` левое число — порт хоста, правое — порт процесса в контейнере. Они совпадают только когда так написали. Один и тот же процесс может слушать 80 внутри, а снаружи его выставляют на разные номера, чтобы несколько контейнеров не заняли один порт хоста.

**NAT** здесь тот же приём, что у сети NAT в VirtualBox, только правила висят на стеке хоста. Исходящий пакет контейнера уходит наружу с адресом машины: подмена источника, MASQUERADE. Входящий пакет на опубликованный порт переписывается в адрес контейнера: подмена назначения. Сосед из другой bridge-сети этого внутреннего адреса не видит, пока его явно не подключили к той же сети.

**Разрешение имён** внутри сети делает DNS демона, а не `/etc/hosts` хоста. Запись появляется, когда контейнер подключается к сети, и пропадает, когда отключается. У сервиса Compose есть постоянное имя на всё время проекта. У одиночного контейнера имя в его сети — это имя контейнера. Короткое имя `localhost` в это разрешение не входит: оно всегда петля самого контейнера.

## f. Docker Compose

Один контейнер описывают командой `docker run`: она сама публикует порт, сама называет том, сама тянет образ. Несколько связанных частей одной такой командой уже не удержать. **Docker Compose** читает файл и приводит демон к описанному состоянию.

Файл декларативный. В нём не написано «сначала скачай, потом подожди, потом запусти». В нём написано, какие сервисы должны быть. `docker compose up -d` сравнивает файл с уже запущенным проектом: недостающее создаёт, повторный запуск не плодит второй экземпляр того же сервиса.

**Сервис** — один образ плюс его настройки: команда, переменные, тома, порты, зависимость от соседей. Типичный стек из трёх сервисов: база, приложение, которое ходит в базу по имени сервиса, и веб-сервер, который публикует порт наружу и проксирует запросы приложению. Несколько compose-файлов можно передать одной команде через повтор `-f`. Общий `--project-directory` склеивает их в один проект, а не в два соседних.

**Сеть** в файле часто не описана. Compose создаёт одну сеть проекта и сажает в неё все сервисы. Коротких имён сервисов тогда достаточно. Отдельный `docker network create` перед этим не нужен. Свою сеть описывают, когда сервисы надо развести по разным сегментам.

**Тома** бывают именованными и привязками к пути. Именованный том хранит файлы в зоне демона, путь на хосте выбирать не надо. Привязка (`/путь/на/хосте:/путь/внутри` или `./файл:путь`) показывает конкретное место на машине. Относительный путь считается от каталога проекта.

**Переменные окружения** подставляются в процесс при создании контейнера. Через них приложение узнаёт адрес базы, имя базы и пароль: адресом служит имя сервиса, а не опубликованный порт. Туда же кладут настройки, которые меняют ссылки, отдаваемые наружу, если перед приложением стоит прокси. Пароль в файле — часть описания стенда. На чужом сервере такой файл не публикуют: секрет тогда лежит в истории репозитория. Его подставляют из окружения или из отдельного файла, который в репозиторий не входит.

**Зависимости** задаёт `depends_on`. Оно задаёт порядок создания контейнеров. Готовность процесса внутри принимать соединения сюда сама не входит: контейнер базы уже `running`, а сервер ещё поднимает файлы. Ожидание готовности добавляют проверкой здоровья (`healthcheck`) и условием в `depends_on`. Без этого ждать умеет только само приложение, если так написан его входной сценарий.

**Управление целиком** идёт по проекту, а не по отдельным именам. `docker compose up -d` поднимает сервисы. `docker compose ps` показывает их вместе. `docker compose logs` собирает журналы. `docker compose down` останавливает и убирает контейнеры и сеть проекта. Именованный том после `down` остаётся. Его удаляет ключ `-v`. Стек выключается одной командой, и данные не путаются с жизнью контейнера.

**Место Compose среди оркестрации** — один компьютер. Файл описывает желаемый набор контейнеров на том демоне, где выполнили команду. Он не переносит сервис на другую машину, если хост выключился, и не держит несколько копий на разных узлах за общим адресом. Это делают кластерные системы: Docker Swarm поверх того же Engine, Kubernetes через containerd, Nomad и другие. У них есть несколько узлов, число реплик, постепенная замена версии и сеть между машинами. Compose остаётся способом записать стенд и локально его поднять. Тот же файл часто служит черновиком манифестов кластера: сервисы, образы, переменные и тома в нём уже названы.

## g. Infrastructure as Code и Docker

**Infrastructure as Code** значит, что сервер, сеть и приложение описаны текстом, и этот текст можно положить в репозиторий, прочитать и выполнить заново. Для Docker таким текстом служат `Dockerfile` и compose-файл.

Три свойства отсюда следуют сами.

**Декларативность.** Compose-файл называет результат: сервис из такого образа, с таким томом и такими переменными. Он не хранит список щелчков и не зависит от того, какие контейнеры уже создавали руками. Демон при `up` приводит машину к файлу. Скрипт из последовательных `docker run` ближе к инструкции «сделай шаги». Он тоже текст, но каждый шаг читают по порядку, а повторный запуск без проверок попытается создать контейнер с тем же именем ещё раз.

**Воспроизводимость.** Другая машина с Docker и тем же каталогом собирает тот же образ и поднимает тот же проект. Предел — в тегах. Имя с версией (`alpine:3.20`) фиксирует линейку. Голое имя без тега означает `latest`: позже pull может привезти другой образ, и файл формально тот же, а содержимое уже другое. Повторяемость становится жёсткой, когда тег дополняют digest.

**Версионирование.** Файл в git помнит, кто поменял порт, прокси или переменную. Откат коммита возвращает описание. Уже запущенный контейнер сам при этом не откатывается: после возврата файла нужен новый `docker compose up` или новая сборка. История инфраструктуры — это история текста плюс заново выполненный текст.

`Dockerfile` — код образа. Из него получается артефакт, который можно тегировать и отправить в реестр. Compose-файл — код уже запущенного стенда: какие образы взять, как назвать их друг для друга, куда положить данные.

**Неизменяемая инфраструктура** означает, что поправку не вносят в живой контейнер. Меняют рецепт или конфиг, заново собирают образ или заново поднимают сервис, старый контейнер заменяют. Изменяемый слой при этом выбрасывается. Каталог, примонтированный с хоста, — отдельный источник данных: он закрывает собой файл из слоя образа на время монтирования. Образ в реестре по-прежнему содержит свою копию. Живой контейнер показывает файл хоста.

**Связь с CI/CD** совпадает с теми же командами. Непрерывная интеграция на коммит запускает `docker build`, проверку и `docker push`. Непрерывная доставка на нужной машине делает `docker pull` и `docker compose up -d`. Секрет в `Dockerfile` не кладут: слой с паролем остаётся в истории образа, даже если следующий шаг файл удалил. Секрет передают переменной при запуске. Веб-панель вроде Portainer стоит сбоку: она показывает, что уже запущено, и умеет забрать образ из реестра. Сборку из git она не заменяет.

## h. Dockerfile и сборка образов

`Dockerfile` — рецепт образа. `docker build -t имя .` читает рецепт, а точкой передаёт контекст: каталог, чьи файлы вообще можно копировать. Файл за пределами контекста в образ не попадёт. Сборка идёт по шагам. Каждый шаг, меняющий файлы, фиксируется как слой. Следующий шаг видит файлы предыдущих и не видит хост, кроме того, что в него явно скопировали.

У рецепта есть устойчивые группы указаний.

База и подписи. `FROM` задаёт первый слой и обязателен. `ARG` до `FROM` передаёт параметр самой сборке, например вариант базы. `LABEL` пишет метаданные. Старое `MAINTAINER` заменено меткой.

Сборка файловой системы. `RUN` выполняет команду и сохраняет результат слоем: поставить пакет, создать каталог. `COPY` берёт файлы из контекста. `ADD` делает то же и ещё умеет распаковать архив и скачать URL, поэтому для обычного файла берут `COPY`. `WORKDIR` задаёт каталог для следующих команд.

Среда и контракт. `ENV` кладёт переменную в образ, она достанется и сборке, и контейнеру. `EXPOSE` записывает, какой порт процесс слушает. `VOLUME` помечает каталог, который при запуске лучше вынести в том. `USER` переключает пользователя, от которого пойдут дальше команды и процесс.

Запуск. `CMD` — команда по умолчанию, её заменяет хвост `docker run` после имени образа. `ENTRYPOINT` — команда, которая выполняется всегда, а хвост `docker run` становится её аргументами. `SHELL` меняет оболочку для строковых форм `RUN` и `CMD`. `STOPSIGNAL` заменяет `SIGTERM` для `docker stop`. `HEALTHCHECK` описывает проверку, после которой демон считает контейнер готовым.

Редкие. `ONBUILD` откладывает указание до тех пор, пока этот образ не станет чьим-то `FROM`. Так собирают заготовки, которые сами копируют исходники потомка.

`EXPOSE` не публикует порт на хосте. Публикация — это `-p` в `docker run` или поле `ports` в Compose. `EXPOSE` только сообщает, какой порт образ считает своим. Без публикации страница с хоста не откроется, даже если указание в рецепте есть. Exec-форма `CMD ["программа", "аргумент"]` запускает программу без `sh -c`. Строковая форма идёт через оболочку.

**Кэширование слоёв.** Демон запоминает шаг вместе с контрольной суммой того, что на него повлияло: текст указания и файлы, которые оно копирует. Если сумма совпала с прошлым разом, слой берётся готовым, команды внутри не повторяются. Первый же изменённый шаг и все шаги ниже пересобираются: нижний слой стал другим, верхние на нём уже не те.

Порядком это пользуются. Редко меняющийся файл копируют раньше того, что правят часто. Правка страницы тогда инвалидирует свой `COPY` и не трогает слой с конфигом и всю стопку базы. Одна команда `COPY . /` на весь каталог пересобирает слой от любой правки. Смена `FROM` пересобирает всё, что ниже.

Кэш локальный. Другая машина его не видит, пока не использует общий кэш сборки. `docker push` отправляет слои, и следующая сборка на той же машине ускоряется за счёт уже лежащих слоёв.

**Многоэтапная сборка** нужна, когда в образ иначе попал бы компилятор. Пишут несколько `FROM`. Первый этап, его помечают `AS build`, ставит компилятор и собирает программу. Последний `FROM` начинает короткий образ, и `COPY --from=build` забирает из первого этапа только готовый файл. Слои с компилятором в итоговый образ не входят. В реестр и в контейнер попадает последний этап. Промежуточный остаётся в кэше сборки. Для страницы или однострочной команды этап один: компилировать нечего, и достаточно маленькой базы.

Компактный и безопасный образ собирают теми же правилами.

- База маленькая и с известной версией. Тег `latest` размер не гарантирует: сегодня образ маленький, завтра в него добавили другой дистрибутив.
- В финальный образ не кладут компилятор, кэш пакетов и исходники. Чистку делают в том же `RUN`, что и установку, иначе кэш останется отдельным слоем. Удаление файла следующим шагом его из предыдущего слоя не выкидывает: слой уже записан.
- Секретов в `COPY` и `RUN` нет. Пароль, попавший в слой, вынимается из истории образа даже после удаления следующим указанием. Пароль передают переменной при запуске.
- Процесс без лишних прав. `USER` переводит PID 1 с root на отдельного пользователя, если серверу не нужен привилегированный порт и чужие файлы.
- Контекст сборки узкий. Случайный файл в каталоге рецепта `COPY` унесёт в слой.

`docker history` после сборки показывает, сколько своих слоёв легло поверх базы.

## i. Эфемерность контейнеров и персистентность данных

Контейнер рассчитан на замену. Образ читается. Всё, что процесс записал поверх, попадает в **изменяемый слой** этого контейнера. Слой появляется вместе с контейнером и удаляется командой `docker rm`. Пересоздание контейнера из того же образа даёт пустой верхний слой. Записи, сделанные в нём, не переносятся.

Короткой команде терять нечего: процесс только печатает и выходит. Файл, положенный в образ через `COPY`, лежит в слое образа. Он переживёт `docker rm` и вернётся при новом `docker run`. Файл, созданный уже внутри работающего контейнера, в образ не попадёт и пропадёт вместе с контейнером. Граница проходит по моменту записи. Сборка пишет в образ. Живой процесс пишет в изменяемый слой, если путь не вынесен наружу.

**Время жизни** изменяемого слоя совпадает с записью контейнера у демона, а не с сессией терминала. Фоновый контейнер можно оставить на ночь, слой сохранится. `docker stop` слой не трогает: следующий `start` видит те же файлы. `docker rm` слой стирает. Образ при этом остаётся.

Данные, которые должны пережить контейнер, кладут вне изменяемого слоя.

**Bind mount** — каталог или файл хоста, видимый по пути внутри контейнера. Запись `-v /данные/на/хосте:/var/lib/mysql` оставляет файлы базы на диске машины. Удаление контейнера этот каталог не удаляет. Монтирование только для чтения (`:ro`) не даёт процессу в контейнере изменить файл хоста. Пока монтирование есть, оно закрывает собой одноимённый путь из слоя образа: снаружи виден файл хоста, а копия из образа спрятана.

**Именованный том** создаёт демон. Каталог лежит в его зоне, обычно под `/var/lib/docker/volumes/`. В compose-файле не надо выбирать путь на хосте. Том виден в `docker volume ls` и переживает `docker compose down`. Он удаляется, когда его явно убрали: `docker volume rm` или `docker compose down -v`. Новый контейнер на том же томе видит прежние файлы. Новый контейнер с пустым томом начинает с пустого каталога.

**tmpfs** — монтирование в памяти. Содержимое есть, пока контейнер запущен, на диск хоста оно не пишется, после остановки его нет. Туда кладут временные файлы и секреты, которые не должны остаться в изменяемом слое и в копии диска.

**Приложение без состояния** можно выкинуть и создать заново из образа, не теряя данных. Статическая страница такая, пока она лежит в образе или в примонтированном каталоге, а не в изменяемом слое. Одноразовая программа такая же: сессия заканчивается вместе с процессом. Контейнер-интерфейс к внешней системе тоже не хранит её данные. Состояние остаётся у той системы, к которой он ходит.

**Приложение с состоянием** копит данные, без которых новая копия процесса бесполезна. База без каталога данных поднимется пустой. Приложение без своих файлов и без базы забудет пользователей. Панель управления без своего тома забудет настройки. Состояние выносят в bind mount или в именованный том. Сам контейнер при этом остаётся заменяемым.

**Резервная копия** снимает это состояние, а не изменяемый слой. Каталог со статическим файлом копируется как обычный файл хоста. Файлы базы на ходу копировать опасно: страницы могут быть записаны наполовину, и копия не откроется. Согласованная копия — это дамп средствами самой базы через `docker exec` либо копирование каталога после `docker stop`, когда сервер закрыл файлы. Именованный том копируют так же: монтируют его в одноразовый контейнер или снимают дамп приложением. Копия лежит отдельно от тома. Том рядом с контейнером защищает от `docker rm` и не защищает от потери диска машины.
