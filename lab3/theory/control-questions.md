# Контрольные вопросы к лабораторной работе №3

Разбор вопросов по Docker. Примеры взяты из этой работы: ноутбук с Fedora, движок из пакета `moby-engine`, плагин Compose из пакета `docker-compose`. Свои образы — `hello-ankudinov` и `lab3-web`. Долгие контейнеры — Nginx на порту 8080, MariaDB с каталогом `/home/DB`, Nextcloud на порту 8088, phpVirtualBox на порту 8081. Проект Compose называется `lab3`: база, Nextcloud и Nginx, снаружи открыт порт 2022. В тот же проект добавлен Portainer. Чужой образ скачан с `ghcr.io` и запущен как игра.

## a. Компоненты платформы Docker

Docker в этой работе — не одна программа. Команда `docker` в терминале Fedora только передаёт просьбу. Контейнер создаёт другая служба, образ хранит третья, а процесс внутри контейнера запускает ещё одна, короткая.

**Клиент** — команда `docker` и команда `docker compose`. Они читают аргументы и файлы в каталоге (`Dockerfile`, `compose.yaml`) и отправляют запрос демону. Сами они не держат Nginx и не распаковывают слои. После `docker run -d` клиент заканчивается, а контейнер `lab3-nginx` остаётся. Связь с демоном идёт через сокет `/var/run/docker.sock`. Группа `docker`, в которую установочный скрипт добавляет пользователя, как раз даёт право писать в этот сокет без `sudo`. Пока группа не применилась, новый вход в систему нужен именно из-за сокета, а не из-за самой команды.

**Демон** — `dockerd`, служба `docker`, которую на Fedora ставит пакет `moby-engine` и включает `systemctl enable --now docker`. Демон принимает запросы клиента, качает образы, собирает слои, заводит сети и тома, помнит контейнеры после закрытия терминала. `docker ps -a` показывает список, который ведёт демон, а не оболочка.

**Реестр** — хранилище образов вне ноутбука. Имя без адреса сервера клиент относит к Docker Hub: так скачиваются `nginx`, `mariadb`, `nextcloud`, `jazzdd/phpvirtualbox`, `portainer/portainer-ce`. Имя с адресом идёт в другой реестр: игра взята как `ghcr.io/bhb603/minesweeper-cli`, это GitHub Container Registry. Свой образ уходит в Hub командами `docker tag` и `docker push`. Реестр хранит слои и подпись «этот тег указывает на вот этот набор слоёв». Запущенных контейнеров в реестре нет.

Поверх этого демона лежат четыре объекта, с которыми работа идёт постоянно.

**Образ** — неизменяемый шаблон файловой системы и команда запуска. `hello-ankudinov` и `lab3-web` собраны локально. `nextcloud` и `mariadb` приехали из реестра. Образ можно удалить, только когда на него не опирается контейнер.

**Контейнер** — запущенный (или уже завершившийся) экземпляр образа. У него есть имя, своя сеть, свой изменяемый слой поверх образа и один главный процесс. `lab3-nginx`, `lab3-mariadb`, `lab3-nextcloud`, `Hello-Ankudinov`, `phpvbox`, `portainer` — разные контейнеры. Два контейнера одного образа делят слои образа и не делят изменяемый слой.

**Том** — место для данных, которое переживает удаление контейнера. В работе два вида. Каталог Fedora примонтирован внутрь: `/home/www/html` у Nginx, `/home/DB` у MariaDB, `/home/www/NextCloud` у Nextcloud. Именованный том заводит сам Docker: `db_data` у базы в Compose и `portainer_data` у Portainer. Файл, записанный просто в контейнер мимо тома, живёт в изменяемом слое и пропадает вместе с контейнером.

**Сеть** — отдельный коммутатор демона. Одиночные `docker run` попадают в сеть `bridge`. Проект Compose получает свою сеть, и в ней имена `db`, `app` и `web` превращаются в адреса. С ноутбука эти имена не открываются: браузер ходит на `localhost` и на опубликованный порт.

**Docker Engine** — это имя всей связки: клиент, демон, API демона, сборка образов, сети и тома. На Fedora пакет называется `moby-engine`, потому что так называется открытый проект движка. Команда в терминале всё равно `docker`, служба всё равно `dockerd`. Рядом пакет `docker-compose` даёт подкоманду `docker compose`. Это тот же Engine, только дистрибутив собрал пакеты сам, а не из репозитория Docker CE.

Дальше демон не запускает процесс контейнера собственными руками. Он просит **containerd**.

containerd — отдельный демон. Он хранит слои как содержимое по адресу-хешу, собирает из них снимок файловой системы и следит за жизненным циклом контейнера. Сборку `Dockerfile`, публикацию портов и compose-файл containerd не разбирает: это остаётся работой dockerd. Разделение полезно тем, что Kubernetes пользуется containerd напрямую, без dockerd. В лабораторной containerd всё равно стоит под Docker: `moby-engine` приносит его как зависимость.

**runc** — программа, которая один раз создаёт контейнер по стандарту OCI. Она получает каталог со корневой файловой системой и файлом `config.json`: какая команда, какие пространства имён, какие лимиты. runc создаёт процесс, настраивает ему изоляцию и завершается. Дальше Nginx или MariaDB — обычные процессы Fedora. Их родитель после выхода runc — маленький процесс-прокладка containerd-shim. Прокладка нужна, чтобы перезапуск dockerd не убил уже запущенные контейнеры: демон можно обновить, а `lab3-nginx` продолжит слушать порт.

Цепочка одного `docker run` в этой работе такая. Клиент пишет в сокет. dockerd находит образ или качает его из реестра, просит containerd подготовить корневую файловую систему и сеть. containerd вызывает runc. runc запускает главный процесс. Клиент к этому моменту уже напечатал идентификатор контейнера и, если указан `-d`, отпустит терминал.

## b. Образы Docker

Образ `lab3-web` собран из трёх указаний:

```dockerfile
FROM nginx:alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY index.html /usr/share/nginx/html/index.html
EXPOSE 8080
```

`docker history lab3-web` показывает эту стопку. Каждая строка, которая меняет файлы, становится **слоем**. `FROM` приносит уже готовую стопку слоёв Nginx и Alpine. Первый `COPY` добавляет слой с конфигом. Второй `COPY` добавляет слой со страницей. `EXPOSE` слой файлов не создаёт: это подпись в метаданных.

Слои только для чтения и адресуются содержимым. Если два образа скачали один и тот же базовый Alpine, на диске этот слой лежит один раз. Контейнеры `lab3-nginx` и любой другой контейнер с `nginx:alpine` читают одни и те же нижние слои.

Склеивает стопку **union-файловая система**. На современном Docker это overlayfs. У каталога, который видит процесс в контейнере, есть нижние каталоги (слои образа) и верхний каталог (изменяемый слой этого контейнера). Чтение файла идёт сверху вниз: если файл есть в верхнем слое, берётся он, иначе поиск продолжается в нижних. Запись в файл из нижнего слоя сначала копирует файл наверх, и дальше меняется уже копия. Это и есть **copy-on-write**. Удаление файла из нижнего слоя не стирает слой: наверху появляется белая метка, и склеенный каталог делает вид, что файла нет. Поэтому образ после `docker build` не переписывается, сколько бы контейнеров от него ни запустили. `docker rm` удаляет верхний каталог контейнера. Слои образа остаются, и следующий `docker run` получает чистый верх.

**Базовый образ** — тот, кто указан во `FROM`, и вся его родословная. У `hello-ankudinov` база — `alpine:3.20`: маленький дистрибутив, в котором достаточно оболочки, чтобы выполнить `echo`. У `lab3-web` база — `nginx:alpine`: тот же Alpine плюс Nginx и его конфиги. Официальные `mariadb` и `nextcloud` тоже чьи-то базы, только их `Dockerfile` в работе не писался. Своя страница не собирает Nginx из исходников. Она принимает уже собранный сервер и кладёт сверху два файла.

**Тег** — удобное имя, которое указывает на конкретный образ. `lab3-web:latest`, `alpine:3.20`, `portainer/portainer-ce:lts`. Часть до двоеточия — имя репозитория, часть после — тег. Если тег не написан, демон подставляет `latest`. Тег можно перевесить: `docker tag lab3-web:latest myuser/lab3-web:latest` не копирует слои, а добавляет второе имя тому же образцу. Завтра `latest` у чужого образа может указывать уже на другую сборку. Поэтому тег — метка, а не отпечаток содержимого.

**Идентификатор** — хеш содержимого. У образа есть `Id`, длинный `sha256:...`. У манифеста в реестре есть свой digest. Манифест перечисляет слои и конфиг. Пока байты слоёв те же, digest тот же. `docker pull nginx@sha256:...` берёт ровно эту сборку, даже если владелец тега `nginx:alpine` уже отправил новую. В работе образы выбирались тегами. Digest нужен, когда одну и ту же сборку надо повторить через месяц.

**Реестр** отдаёт и принимает эти манифесты и слои по HTTPS. Docker Hub — реестр по умолчанию и одновременно сайт, где у образа есть страница. Имя `jazzdd/phpvirtualbox` значит: реестр Hub, пользователь или организация `jazzdd`, репозиторий `phpvirtualbox`. Имя `ghcr.io/bhb603/minesweeper-cli` значит: реестр уже не Hub. Локальный образ `hello-ankudinov` в реестре не появляется, пока его не пометили именем вида `<логин>/<репозиторий>` и не выполнили `docker push`. Push отправляет только те слои, которых у реестра ещё нет. Базовый `nginx:alpine` при публикации `lab3-web` повторно заливается лишь в той части, которой у Hub нет.

Получение симметрично. `docker pull` качает манифест и недостающие слои. `docker run` с образом, которого нет локально, делает pull сам. Так в работе появились MariaDB, Nextcloud и phpVirtualBox. Свой `lab3-web` pull не требует: его произвёл `docker build` на этой Fedora.

## c. Жизненный цикл контейнеров

Контейнер для демона — запись с состоянием. Процесс внутри может уже закончиться, а запись ещё лежать в `docker ps -a`.

Состояния, которые видны в этой работе:

- **created** — запись есть, главный процесс не запущен. `docker create` останавливается на этом. Скрипты лабораторной сразу идут в `docker run`, поэтому отдельно это состояние почти не задерживается.
- **running** — главный процесс жив. Так работают `lab3-nginx`, `lab3-mariadb`, `lab3-nextcloud`, `phpvbox`, сервисы Compose и Portainer, пока их не остановят.
- **paused** — процесс заморожен целиком, через cgroup freezer. Память и открытые файлы остаются. `docker pause` в работе не использовался. Это не остановка: порт ещё занят, процесс не получил сигнал завершиться.
- **exited** — главный процесс завершился. `Hello-Ankudinov` печатает строку и сразу оказывается здесь: команда `echo` сделала своё и вышла. В `docker ps` его нет, в `docker ps -a` он есть, вместе с кодом выхода.
- **restarting** — процесс умер, а политика перезапуска велит поднять его снова. Контейнер на короткое время виден в этом состоянии, затем снова `running` или, после исчерпания попыток, `exited`.

Переходы прямые. `create` даёт `created`. `start` переводит `created` или `exited` в `running`. `docker run` сливает создание и старт. `stop` переводит `running` в `exited`. Повторный `start` поднимает тот же контейнер с тем же изменяемым слоем, а не собирает новый. `rm` удаляет запись и изменяемый слой. Удалить можно вышедший контейнер. `docker rm -f` сначала останавливает, потом удаляет.

**Главный процесс** — PID 1 внутри контейнера. Контейнер жив, пока жив он. В `hello-ankudinov` это `echo`: форма `CMD ["echo", "..."]` запускает его напрямую, без оболочки. В `lab3-web` это Nginx на переднем плане. У MariaDB и Nextcloud входной сценарий образа в конце подменяет себя сервером, и сервер становится PID 1. Когда PID 1 завершается, containerd помечает контейнер как `exited`. Остальные процессы контейнера при этом получают завершение вместе с ним.

`docker exec` запускает добавочный процесс рядом с PID 1. Команда `docker exec lab3-mariadb mariadb ... -e "CREATE DATABASE ankudinov"` не заменяет сервер базы. Клиент `mariadb` подключается к уже работающему серверу, создаёт базу и сам заканчивается. Сервер остаётся PID 1. Если бы завершился сервер, контейнер перешёл бы в `exited`, даже если клиент ещё что-то печатал.

PID 1 в Linux получает ещё одну обязанность: он должен забирать завершившихся потомков и принимать сигналы. Обычный процесс, который не является PID 1, получает действие по умолчанию на многие сигналы и не видит чужих зомби. Поэтому образ и устроен так, чтобы сервер был PID 1, а не чтобы перед ним всю жизнь висела оболочка `sh -c`. Оболочка без специальной передачи сигнала съедает `SIGTERM` сама и не отдаёт его серверу. Exec-форма `CMD` в hello-образе как раз обходит оболочку.

**Корректная остановка** — `docker stop`. Демон посылает PID 1 сигнал `SIGTERM` и ждёт, по умолчанию 10 секунд. Nginx закрывает соединения и выходит. MariaDB сбрасывает грязные страницы и останавливает движок. После этого файлы в `/home/DB` согласованы, и следующий старт обходится без восстановления после аварии. Если процесс за это время не вышел, демон посылает `SIGKILL`. `SIGKILL` процесс не перехватывает: ядро снимает его сразу.

**Принудительная остановка** — `docker kill`. По умолчанию это сразу `SIGKILL`, без ожидания и без `SIGTERM`. Для базы это то же самое, что выдернуть питание. Журнал InnoDB при следующем старте доиграет сам, но транзакция, которая не успела зафиксироваться, откатится. Для hello-контейнера разницы нет: процесс и так уже завершён. Для MariaDB разница есть, поэтому в работе сервер оставляют работать и ходят в него через `docker exec`, а не снимают его сигналом `KILL`.

`docker restart` — это stop и затем start того же контейнера. Изменяемый слой и примонтированные каталоги сохраняются. Новый контейнер получился бы только из нового `docker run`.

## d. Режимы запуска контейнеров

**Фоновый режим** включает ключ `-d`. Клиент просит демон запустить контейнер и сразу возвращает терминал. Так запущены `lab3-nginx`, `lab3-mariadb`, `lab3-nextcloud`, `phpvbox` и сервисы `docker compose up -d`. Вывод процесса в терминал не течёт. Его забирает `docker logs`. Порт при этом слушается, даже когда окно терминала закрыто: процесс держит демон, а не сессия оболочки.

**Интерактивный режим** — ключи `-it`. `-i` оставляет открытым стандартный ввод, `-t` выделяет терминал, чтобы у программы были управляющие последовательности. Игра запускается как `docker run -it ghcr.io/bhb603/minesweeper-cli`: без терминала ей некуда рисовать поле и неоткуда читать ходы. Пока игра запущена, этот терминал занят. Закрытие игры завершает главный процесс, и контейнер переходит в `exited`.

`Hello-Ankudinov` запускается на переднем плане, но без `-it`. Ему не нужен ввод. Клиент просто ждёт, пока `echo` напечатает строку и выйдет, и показывает этот вывод. Это передний план, и это одноразовый запуск.

**Одноразовый контейнер** существует ради одного действия. Hello печатает строку. Клиент `mariadb` внутри `docker exec` создаёт базу и заканчивается. Игра живёт одну партию. Образ после этого остаётся, запись контейнера можно удалить. Повторять действие — значит создать новый процесс, а не «продолжить» старый.

**Долгоживущий контейнер** держит сервер. Nginx ждёт HTTP-запросы на порту 8080. MariaDB ждёт подключения на 3306. Nextcloud ждёт браузер. Portainer ждёт свой веб-интерфейс. Их PID 1 не должен завершаться после настройки. Официальные образы поэтому запускают сервер на переднем плане внутри контейнера, а не в режиме демона классического Unix: если бы Nginx ушёл в фон и родительский сценарий закончился, контейнер сразу стал бы `exited`.

**Политика перезапуска** говорит демону, что делать, когда PID 1 умер или когда перезапустилась сама служба `docker`.

- `no`, значение по умолчанию. Контейнер остаётся `exited`. Так ведут себя hello и контейнеры без ключа `--restart`.
- `on-failure` поднимает контейнер снова, только если код выхода ненулевой. Успешный конец hello (код 0) его не перезапустит.
- `always` поднимает контейнер и после падения, и когда снова стартовал демон. В `portainer.yaml` у сервиса стоит `restart: always`.
- `unless-stopped` делает то же, пока контейнер не остановлен вручную. После `docker stop` перезапуск демона оставляет его выключенным. У phpVirtualBox в скрипте как раз `--restart unless-stopped`: интерфейс к VirtualBox должен вернуться после перезагрузки Fedora и не должен воскреснуть, если его остановили специально.

Политика не создаёт второй контейнер. Она снова переводит ту же запись в `running`.

**Ограничение ресурсов** делает cgroup, не образ. Ключи `--memory`, `--cpus`, `--pids-limit` ставят потолок этому контейнеру. В скриптах работы потолков нет: Nginx и MariaDB берут процессор и память Fedora наравне с остальными процессами, пока ядро само не начнёт отбирать память. Потолок нужен, когда на одной машине несколько долгих контейнеров и один из них не должен забрать всё. Исчерпание памяти cgroup завершает процессы контейнера. Исчерпание квоты CPU его не убивает, а замедляет.

**Изоляция** — набор пространств имён Linux, которые runc включает процессу.

- PID: внутри контейнера свой список процессов, PID 1 — его сервер. Процессы Fedora снаружи он не видит.
- Mount: свой корень файловой системы, собранный из слоёв и томов. Каталог хоста виден только там, куда его примонтировали.
- Network: свой стек, свои порты, свой `localhost`. `localhost` внутри `lab3-nginx` — это сам Nginx, а не Fedora.
- UTS: своё имя хоста, обычно идентификатор контейнера.
- IPC: своя разделяемая память.

Пользовательское пространство имён Docker по умолчанию не включает. Root внутри контейнера — это uid 0 на Fedora, только с урезанными возможностями. Защита держится на capabilities и на том, что монтирования и устройства контролирует демон.

**Привилегии.** Обычный контейнер не может грузить модули ядра, перенастраивать сеть хоста и читать чужие диски. Ключ `--privileged` снимает почти все эти запреты и отдаёт устройства. В работе он не нужен. phpVirtualBox управляет VirtualBox по сети: `vboxwebsrv` слушает порт 18083 на Fedora, контейнер ходит на адрес моста `172.17.0.1`. Отдельная привилегия в работе есть у Portainer. Ему в контейнер отдан `/var/run/docker.sock`. Кто может писать в этот сокет, тот может просить демон запускать любые контейнеры, в том числе привилегированные. Порт 9443 снаружи выглядит как обычный веб-интерфейс, а сокет рядом делает этот контейнер администратором всего Docker на ноутбуке.

## e. Типы сетей Docker

Демон умеет несколько **драйверов**. В работе реально заняты два.

**bridge** — коммутатор на хосте и пара виртуальных кабелей `veth` до каждого контейнера. Контейнер получает адрес из диапазона моста, обычно `172.17.0.0/16` у сети по умолчанию. Выход в интернет идёт через трансляцию адресов хоста. Одиночные `docker run` без `--network` попадают сюда. phpVirtualBox поэтому видит Fedora как `172.17.0.1`: это адрес моста `docker0` со стороны хоста, и на нём слушает `vboxwebsrv`.

**Сеть проекта Compose** — тоже bridge, только свой, с именем вроде `lab3_default`. Сервисы `db`, `app` и `web` подключены к ней и не обязаны быть в сети `docker0`. Своя сеть и есть граница изоляции: контейнер из `docker run` не резолвит имя `app`, даже если оба контейнера запущены на одной Fedora.

Остальные драйверы в работе не включались, но вопрос про типы без них не закрывается.

- **host** отдаёт контейнеру сетевое пространство имён Fedora. Порт 80 внутри был бы портом 80 ноутбука, публиковать его не нужно. Изоляции адресов нет.
- **none** не выдаёт интерфейсов, кроме петли. Контейнеру некуда отправить пакет.
- **overlay** строит одну сеть поверх нескольких хостов. Его использует Swarm. На одном ноутбуке он ничего не добавляет к bridge.
- **macvlan** и **ipvlan** выдают контейнеру адрес прямо в физической сети, как отдельной машине на коммутаторе. Мост Docker и трансляция портов при этом не стоят посередине.

**Изоляция сетей** означает, что демон не маршрутизирует пакеты между двумя bridge сам. Опубликованный порт — отдельное правило, и оно ведёт с хоста в конкретный контейнер, а не открывает всю сеть наружу. MariaDB в Compose не имеет секции `ports`, поэтому с Fedora к ней не подключиться по `localhost:3306`. К ней подключается Nextcloud по имени `db` и порту 3306 уже внутри сети проекта. Отдельный контейнер `lab3-mariadb` как раз публикует `3306:3306`, потому что клиент с хоста должен попасть внутрь.

**Взаимодействие контейнеров** на одной сети идёт по их адресам. Имена выдаёт встроенный DNS демона, `127.0.0.11` с точки зрения контейнера. Имя сервиса из `compose.yaml` становится именем: `db` — база, `app` — Nextcloud. Конфиг Nginx в проекте поэтому содержит `proxy_pass http://app:80`. Этот `app` существует только пока оба сервиса в одной сети Compose. С ноутбука то же имя не откроется.

**Публикация портов** — правило на хосте: пакет на порт Fedora переписывается в адрес контейнера и в его порт. В работе пары такие:

- `8080:8080` — свой Nginx, он слушает 8080 и внутри, и снаружи;
- `3306:3306` — отдельная MariaDB;
- `8088:80` — отдельный Nextcloud, внутри образ слушает 80;
- `8081:80` — phpVirtualBox;
- `2022:80` — Nginx проекта Compose, который дальше проксирует на `app:80`;
- `9443:9443` и `8000:8000` — Portainer.

Левое число — порт Fedora, правое — порт процесса в контейнере. Они совпадают только когда так написали. Nextcloud везде слушает 80. Меняется наружный номер, чтобы несколько контейнеров не заняли один порт хоста.

**NAT** здесь тот же приём, что у сети NAT в VirtualBox, только правила висят на сетевом стеке Fedora. Исходящий пакет контейнера уходит в интернет с адресом ноутбука: подмена источника, MASQUERADE. Входящий пакет на опубликованный порт переписывается в адрес контейнера: подмена назначения. Соседний контейнер в другой bridge-сети этого внутреннего адреса не видит, пока его явно не подключили к той же сети. Обратный адрес уходит через те же правила, поэтому ответ на запрос к `localhost:2022` возвращается браузеру.

**Разрешение имён** внутри сети делает DNS демона, а не `/etc/hosts` Fedora. Запись появляется, когда контейнер подключается к сети, и пропадает, когда отключается. У сервиса Compose есть постоянное имя на всё время проекта. У одиночного контейнера имя в его сети — это имя контейнера. Короткое имя `localhost` в это разрешение не входит: оно всегда петля самого контейнера.

## f. Docker Compose

Одиночные контейнеры в работе описаны командами `docker run`: каждая сама публикует порт, сама называет том, сама тянет образ. Проект из трёх частей одной такой командой уже не удержать. **Docker Compose** читает файл и приводит демон к описанному состоянию.

Файл `compose.yaml` декларативный. В нём не написано «сначала скачай, потом подожди, потом запусти». В нём написано, какие сервисы должны быть. `docker compose up -d` сравнивает файл с уже запущенным проектом `lab3`: недостающее создаёт, лишнее по этому файлу не трогает, если оно из другого проекта. Повторный запуск той же команды не плодит вторую базу. Он убеждается, что сервисы на месте.

**Сервисы** в файле — `db`, `app` и `web`.

- `db` — образ `mariadb`, пароль и имя базы в переменных, том `db_data`.
- `app` — образ `nextcloud`. Переменная `MYSQL_HOST: db` говорит ему, где база. Каталог `/home/www/NextCloud` примонтирован в `/var/www/html`.
- `web` — образ `nginx`. Он публикует `2022:80` и конфигом проксирует запросы на `app:80`.

Portainer добавлен вторым файлом `portainer.yaml`. Команда запускает оба файла сразу и указывает `--project-directory` на каталог первого, чтобы это был тот же проект `lab3`, а не отдельный. Сервис `portainer` появляется рядом с тремя остальными.

**Сеть** в файле не описана. Compose создаёт одну сеть проекта и сажает в неё все сервисы. Из-за этого коротких имён `db` и `app` достаточно. Отдельный `docker network create` перед этим не нужен.

**Тома** описаны явно. `db_data` — именованный том проекта, файлы базы лежат в каталоге демона. `/home/www/NextCloud` и `./nginx.conf` — привязки к путям Fedora. Конфиг Nginx должен лежать рядом с `compose.yaml`, потому что относительный путь считается от каталога проекта. `portainer_data` объявлен во втором файле и хранит пароль и настройки веб-интерфейса.

**Переменные окружения** подставляются в процесс контейнера при создании. Nextcloud по `MYSQL_HOST`, `MYSQL_DATABASE`, `MYSQL_USER` и `MYSQL_PASSWORD` сам выполняет установку в уже существующую базу. `OVERWRITEHOST: localhost:2022` и `OVERWRITEPROTOCOL: http` заставляют его отдавать ссылки на тот адрес, по которому к нему приходят через Nginx, а не на внутреннее имя `app`. Пароли в файле — часть описания стенда. Для лабораторной это нормально. Для чужого сервера такой файл не публикуют: пароль тогда лежит в истории репозитория.

**Зависимости** задаёт `depends_on`. `app` ждёт, пока создан контейнер `db`, `web` ждёт контейнер `app`. Это порядок старта контейнеров. Готовность MariaDB принимать соединения сюда не входит: контейнер базы уже `running`, а сервер внутри ещё поднимает файлы. У официального образа Nextcloud входной сценарий умеет подождать базу. Сам Compose без проверки здоровья про это не знает.

**Управление целиком** идёт по проекту, а не по трём именам. `docker compose up -d` поднимает сервисы. `docker compose ps` показывает их вместе. `docker compose logs` собирает журналы. `docker compose down` останавливает и убирает контейнеры и сеть проекта. Именованный том `db_data` после `down` остаётся. Он удаляется отдельным ключом `-v`. Так стек выключается одной командой, и данные базы не путаются с жизнью контейнера.

**Место Compose среди оркестрации** — один компьютер. Файл описывает желаемый набор контейнеров на том демоне, где выполнили команду. Он не переносит `app` на другой ноутбук, если Fedora выключилась, и не держит две копии Nextcloud на двух машинах с общим адресом. Это делают кластерные системы: Docker Swarm поверх того же Engine, Kubernetes через containerd, Nomad и другие. У них есть несколько узлов, число реплик, постепенная замена версии и своя сеть между машинами. Compose остаётся способом записать стенд и локально его поднять. Тот же файл часто служит черновиком, по которому потом пишут манифесты кластера: сервисы, образы, переменные и тома в нём уже названы.

## g. Infrastructure as Code и Docker

**Infrastructure as Code** значит, что сервер, сеть и приложение описаны текстом, и этот текст можно положить в репозиторий, прочитать и выполнить заново. В работе таким текстом служат `Dockerfile`, `compose.yaml`, `nginx.conf` и скрипты запуска.

Три свойства отсюда следуют сами.

**Декларативность.** `compose.yaml` называет результат: сервис `db` из образа `mariadb` с таким томом и такими переменными. Он не хранит список щелчков мышью и не зависит от того, какие контейнеры кто-то уже создавал руками в другой день. Демон при `up` приводит машину к файлу. Скрипт из последовательных `docker run` ближе к инструкции «сделай шаги». Он тоже текст, но каждый шаг надо читать по порядку, а повторный запуск без проверок попытается создать контейнер с тем же именем ещё раз.

**Воспроизводимость.** Другая Fedora с установленным Docker и этим каталогом собирает тот же `lab3-web` и поднимает тот же проект. Предел воспроизводимости — в тегах. `alpine:3.20` и `portainer/portainer-ce:lts` фиксируют линейку. Голое имя `mariadb` или `nextcloud` означает тег `latest`: через полгода pull может привезти другой образ, и файл формально тот же, а содержимое уже другое. Повторяемость становится жёсткой, когда тег дополняют digest.

**Версионирование.** Файл в git помнит, кто поменял порт, прокси или переменную. Откат коммита возвращает описание. Раскатанный контейнер сам при этом не откатывается: после возврата файла нужен новый `docker compose up` или новая сборка образа. История инфраструктуры — это история текста плюс заново выполненный текст.

`Dockerfile` — код образа. Из него получается артефакт `lab3-web`, который можно тегировать и отправить в реестр. `compose.yaml` — код уже запущенного стенда: какие образы взять, как назвать их друг для друга, куда положить данные. Вместе они заменяют устную схему «поставь Nginx, пропиши порт, не забудь каталог».

**Неизменяемая инфраструктура** означает, что поправку не вносят в живой контейнер. Не заходят в `lab3-nginx` и не правят конфиг, надеясь вспомнить это через месяц. Меняют `nginx.conf` или `Dockerfile`, заново собирают образ или заново поднимают сервис, старый контейнер заменяют. Изменяемый слой при этом выбрасывается. Исключение в работе сделано сознательно там, где задание требует каталог хоста: страница отдаётся из `/home/www/html`, потому что каталог примонтирован поверх слоя, куда `COPY` положил `index.html`. Образ в реестре по-прежнему содержит свою копию страницы. Живой контейнер показывает файл Fedora. Это два разных источника, и путаются они только пока монтирование включено.

**Связь с CI/CD** прямая по шагам, даже когда шаги в лабораторной выполнены руками. Непрерывная интеграция на каждый коммит запускала бы `docker build`, проверку и `docker push` — ровно те команды, которыми `lab3-web` уходит в Hub. Непрерывная доставка на нужной машине делала бы `docker pull` и `docker compose up -d`, чтобы поднять уже отправленный образ. Секреты в таком конвейере не кладут в `Dockerfile`: слой с паролем остаётся в истории образа. Их передают переменными при запуске, как пароль MariaDB в Compose. Portainer в этой цепочке стоит сбоку. Он показывает, что уже запущено, и умеет забрать образ из реестра. Сборку из git он в работе не заменяет.

## h. Dockerfile и сборка образов

`Dockerfile` — рецепт образа. `docker build -t lab3-web .` читает рецепт, а точкой передаёт контекст: каталог, чьи файлы вообще можно копировать. Файл за пределами контекста в образ не попадёт. Сборка идёт по шагам. Каждый шаг, меняющий файлы, фиксируется как слой. Следующий шаг видит файлы предыдущих и не видит хост, кроме того, что в него явно скопировали.

У рецепта есть устойчивые группы указаний.

База и подписи. `FROM` задаёт первый слой и обязателен. `ARG` до `FROM` передаёт параметр самой сборке, например вариант базы. `LABEL` пишет метаданные. Старое `MAINTAINER` заменено как раз меткой.

Сборка файловой системы. `RUN` выполняет команду и сохраняет результат слоем: поставить пакет, создать каталог. `COPY` берёт файлы из контекста. `ADD` делает то же и ещё умеет распаковать архив и скачать URL, поэтому для обычного файла берут `COPY`. `WORKDIR` задаёт каталог для следующих команд.

Среда и контракт. `ENV` кладёт переменную в образ, она достанется и сборке, и контейнеру. `EXPOSE` записывает, какой порт процесс слушает. `VOLUME` помечает каталог, который при запуске лучше вынести в том. `USER` переключает пользователя, от которого пойдут дальше команды и процесс.

Запуск. `CMD` — команда по умолчанию, её заменяет хвост `docker run` после имени образа. `ENTRYPOINT` — команда, которая выполняется всегда, а хвост `docker run` становится её аргументами. `SHELL` меняет оболочку, через которую выполняют строковые формы `RUN` и `CMD`. `STOPSIGNAL` заменяет `SIGTERM` для `docker stop`. `HEALTHCHECK` описывает проверку, после которой демон считает контейнер готовым.

Редкие. `ONBUILD` откладывает указание до тех пор, пока этот образ не станет чьим-то `FROM`. Так собирают заготовки, которые сами копируют исходники потомка.

В двух рецептах работы использованы четыре указания. `hello-ankudinov`: `FROM alpine:3.20` и `CMD ["echo", "Hello, Анкудинов К. К. Группа P3418"]`. Квадратные скобки — exec-форма: демон запускает `echo` без `sh -c`. `lab3-web`: `FROM nginx:alpine`, два `COPY` и `EXPOSE 8080`. `EXPOSE` не публикует порт на Fedora. Публикация — это `-p 8080:8080` в `docker run`. `EXPOSE` только сообщает, какой порт образ считает своим. Без `-p` страница с ноутбука не откроется, даже если указание в рецепте есть.

**Кэширование слоёв** устроено так. Демон запоминает шаг вместе с контрольной суммой того, что на него повлияло: текст указания и файлы, которые оно копирует. Если сумма совпала с прошлым разом, слой берётся готовым, команды внутри не повторяются. Первый же изменённый шаг и все шаги ниже пересобираются: нижний слой стал другим, верхние на нём уже не те.

Порядок в `lab3-web` этим пользуется. Конфиг копируется раньше страницы. Правка `index.html` инвалидирует второй `COPY` и не трогает слой с `nginx.conf` и всю стопку `nginx:alpine`. Если бы оба файла копировались одной командой `COPY . /`, любая правка страницы пересобирала бы и конфиг. `FROM` в начале значит обратное для всей стопки: смена базового образа пересобирает всё, что ниже.

Кэш локальный. Другая машина его не видит, пока не использует общий кэш сборки. `docker push` отправляет слои, и следующая сборка на том же ноутбуке снова ускоряется за счёт уже лежащих слоёв.

**Многоэтапная сборка** в этих двух рецептах не нужна: страница и `echo` ничего не компилируют. Приём нужен, когда в образ попадает компилятор. Пишут несколько `FROM`. Первый этап, его помечают `AS build`, ставит компилятор и собирает программу. Последний `FROM` начинает короткий образ, и `COPY --from=build` забирает из первого этапа только готовый файл. Слои с компилятором в итоговый образ не входят. В реестр и в контейнер попадает второй этап. Промежуточный остаётся в кэше сборки. Для `lab3-web` тот же смысл уже выполнен выбором базы: Nginx не собирается из исходников на каждой машине, в образ добавляются два файла.

Компактный и безопасный образ собирают теми же правилами.

- База маленькая и с известной версией. `alpine:3.20` для hello этим и выбран. Чужой тег `latest` компактность не гарантирует: сегодня он маленький, завтра в него добавили другой дистрибутив.
- В финальный образ не кладут компилятор, кэш пакетов и исходники. Многоэтапная сборка и чистка в том же `RUN`, что и установка, не оставляют кэш отдельным слоем. Удаление файла следующим шагом его из предыдущего слоя не выкидывает: слой уже записан.
- Секретов в `COPY` и `RUN` нет. Пароль, попавший в слой, вынимается из истории образа даже после «удаления» следующим указанием. Пароль базы в работе передаётся переменной при запуске.
- Процесс без лишних прав. `USER` переводит PID 1 с root на отдельного пользователя, если серверу не нужен порт ниже 1024 и не нужны чужие файлы. Официальный Nginx стартует с правами, которые нужны ему, чтобы открыть журнал и потом опустить рабочие процессы. Свой рецепт этого не меняет.
- Контекст сборки узкий. В каталог рецепта не кладут случайные файлы, иначе `COPY` унесёт их в слой. Чем меньше контекст, тем меньше лишнего на диске и в реестре.

`docker history lab3-web` после сборки как раз показывает, что своего в образе два тонких слоя поверх чужого Nginx, а не копия всей Fedora.

## i. Эфемерность контейнеров и персистентность данных

Контейнер рассчитан на замену. Образ читается. Всё, что процесс записал поверх, попадает в **изменяемый слой** этого контейнера. Слой появляется вместе с контейнером и удаляется командой `docker rm`. Пересоздание контейнера из того же образа даёт пустой верхний слой. Записи, сделанные в нём, не переносятся.

Для `Hello-Ankudinov` это ничего не ломает: процесс только печатает строку. Для Nginx страница, положенная в образ через `COPY`, лежит в слое образа, а не в изменяемом слое. Она переживёт `docker rm` и вернётся при новом `docker run`. Файл, созданный уже внутри работающего контейнера командой `docker exec`, в образ не попадёт и пропадёт вместе с контейнером. Граница проходит по моменту записи. Сборка пишет в образ. Живой процесс пишет в изменяемый слой, если путь не вынесен наружу.

**Время жизни** изменяемого слоя совпадает с записью контейнера у демона, а не с сессией терминала. Фоновый `lab3-nginx` можно оставить на ночь, слой сохранится. `docker stop` слой не трогает: следующий `start` видит те же файлы. `docker rm` слой стирает. Образ `lab3-web` при этом остаётся.

Данные, которые должны пережить контейнер, кладут вне изменяемого слоя. В работе для этого два механизма.

**Bind mount** — каталог или файл Fedora, видимый по пути внутри контейнера.

- `/home/www/html` → `/usr/share/nginx/html` у `lab3-nginx`, только чтение. Страница в браузере — это файл хоста. Он закрывает собой `index.html` из слоя образа, пока монтирование есть.
- `/home/DB` → `/var/lib/mysql` у `lab3-mariadb`. После `CREATE DATABASE ankudinov` файлы этой базы лежат на диске Fedora. `sudo ls /home/DB` показывает их снаружи. Удаление контейнера каталог не удаляет.
- `/home/www/NextCloud` → `/var/www/html` у отдельного Nextcloud и у сервиса `app`. Установленные файлы Nextcloud оказываются на хосте.

Один и тот же каталог Nextcloud не стоит отдавать двум процессам сразу. Отдельный контейнер без переменных `MYSQL_*` хранит свои данные в SQLite внутри этого каталога. Сервис Compose указывает на MariaDB и монтирует тот же путь. Это два способа поднять Nextcloud по заданию, и одновременно они писали бы в одни файлы.

**Именованный том** создаёт демон, каталог лежит в его зоне, обычно под `/var/lib/docker/volumes/`. В Compose это `db_data` для MariaDB проекта и `portainer_data` для настроек Portainer. В `compose.yaml` не надо выбирать путь на Fedora. Том виден в `docker volume ls` и переживает `docker compose down`. Он удаляется, когда его явно убрали: `docker volume rm` или `docker compose down -v`. Пароль администратора Portainer живёт в `portainer_data`. Новый контейнер Portainer на том же томе поднимается уже настроенным. Новый контейнер с пустым томом снова спрашивает пароль.

**tmpfs** — монтирование в памяти. Содержимое есть, пока контейнер запущен, на диск Fedora оно не пишется, после остановки его нет. Туда кладут временные файлы и секреты, которые не должны остаться в изменяемом слое и в копии диска. В скриптах работы tmpfs нет: странице, базе и Nextcloud как раз нужно пережить остановку.

**Приложение без состояния** можно выкинуть и создать заново из образа, не теряя данных. Статическая страница Nginx такая, пока страница лежит в образе или в примонтированном каталоге, а не в изменяемом слое. Игра с `ghcr.io` такая же: партия заканчивается вместе с процессом, следующим запуском создаётся новый контейнер. phpVirtualBox тоже не хранит виртуальные машины. Машины и их диски остаются у VirtualBox на Fedora. Контейнер только рисует интерфейс к `vboxwebsrv`.

**Приложение с состоянием** копит данные, без которых копия процесса бесполезна. MariaDB без каталога данных поднимется пустой: базы `ankudinov` не будет. Nextcloud без своих файлов и без базы забудет пользователей. Portainer без своего тома забудет пароль администратора. Состояние в работе вынесено в `/home/DB`, `/home/www/NextCloud`, `db_data` и `portainer_data`. Контейнеры при этом остаются заменяемыми.

**Резервная копия** снимает именно это состояние, а не изменяемый слой. Каталог `/home/www/html` копируется как обычный файл Fedora: страница одна. С базой так делать на ходу опасно. Файлы InnoDB в `/home/DB` в момент копирования могут быть наполовину записаны, и копия не откроется. Согласованная копия — это `mariadb-dump` через `docker exec` в момент работы сервера либо копирование `/home/DB` после `docker stop`, когда сервер закрыл файлы сам. Именованный том копируют так же, предварительно смонтировав его в одноразовый контейнер, или снимают дамп приложением. Копия лежит отдельно от тома. Том рядом с контейнером защищает от `docker rm` и не защищает от потери диска ноутбука.
